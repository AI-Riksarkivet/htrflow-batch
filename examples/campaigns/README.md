# A campaigns repo, in shape

This is what a real campaigns repo looks like — the input to
`htrflow-campaigns` (`packages/converter` in
[htrflow-batch](https://github.com/AI-Riksarkivet/htrflow-batch)). Copy this
directory as the starting point for your own repo; I15 (a future story)
creates the real, permanent one.

```
converter.yaml            # cluster-wide defaults: namespace, queue, window, S3 secret, PVC, …
campaigns/<name>.yaml      # what to run: a pipeline id + a list of volumes
pipelines/<id>.yaml        # how to run it: a digest-pinned image + htrflow steps
rendered/                  # generated by CI on main — never hand-edited, see below
.github/workflows/render.yml
```

Full field-by-field rules: htrflow-batch's
[`docs/reference/campaign-yaml.md`](https://github.com/AI-Riksarkivet/htrflow-batch/blob/main/docs/reference/campaign-yaml.md)
and [`docs/how-it-works/campaigns.md`](https://github.com/AI-Riksarkivet/htrflow-batch/blob/main/docs/how-it-works/campaigns.md).

## The two rules

Everything about operating a campaigns repo reduces to these two. They are
Kubernetes semantics, not policy this repo invents — they are true because a
campaign **is** one Kubernetes Indexed Job:

> **Pausing a campaign is a Git change.** Set `suspend: true` in
> `campaigns/<name>.yaml` — never `kubectl edit` the Job, or the next
> render/apply cycle silently undoes your change. The rendered Job carries
> `spec.suspend: true`, but Kueue owns that field for a Workload it has
> admitted, so the apply step also patches the Workload's `spec.active`
> (`scripts/kueue-pause-sync.sh`, run by `make campaigns-apply` or as an
> Argo CD `PostSync` hook). Declared in Git, enforced at apply time.
>
> **Deleting a campaign's file cancels it** — *if the apply prunes*. The
> next `render` removes its file from `rendered/`, and the apply that follows
> deletes its Job and its `volumes.txt` ConfigMap only when pruning is turned
> on: Argo CD needs `syncPolicy.automated.prune: true` (it defaults to
> `false`, and a manual sync prunes only with `--prune`), and on a PoC it is
> `make campaigns-apply PRUNE=1`, which runs
> `kubectl apply --prune -l htrflow.riksarkivet.se/managed-by=converter`
> (a plain apply never deletes anything). **Results already published to S3
> are never touched by anything in this system — not by pausing, not by
> cancelling.**

## Adding a campaign

1. Add (or reuse) a pipeline in `pipelines/<id>.yaml` — a digest-pinned
   wrapper image and the htrflow `steps:` document. A pipeline id is a
   **permanent name for a recipe**: once any campaign has run against it,
   treat the file as immutable — to change the recipe, mint a new id
   (`demo-v2.yaml`) instead of editing this one. This is a review
   convention (there is no server-side enforcement any more), so protect
   `main` and require review on this repo.
2. Add a new file under `campaigns/<name>.yaml` naming that pipeline and
   the volumes to run.
3. Open a PR. CI runs `htrflow-campaigns validate` on it.
4. Merge. CI on `main` runs `htrflow-campaigns render` and commits the
   result under `rendered/` (see `.github/workflows/render.yml`). Whatever
   applies `rendered/` to a cluster — Argo CD watching this repo, or
   `make campaigns-apply` by hand on a PoC — picks it up from there.

## The append-only rule

**A campaign is append-only.** A Kubernetes Job's `completions` count is
fixed at creation from the volume list — it is not something Kubernetes
lets you change on a running Job. `htrflow-campaigns render` enforces this
at render time: if you edit an existing `campaigns/<name>.yaml`'s volume
list after it has already been rendered once, `render` refuses and prints
`campaign <name> is append-only: create a new campaign`.

To add more volumes to an ongoing effort, create a new campaign file
instead (`demo-2.yaml`, `demo-batch-2.yaml`, whatever naming makes the
relationship obvious) rather than editing the first one. Both campaigns'
results land in the same place (same pipeline id ⇒ same S3 prefix), so
nothing about "where do results go" changes — only which Job is tracking
which volumes.

## `rendered/`

Generated, not hand-authored. `htrflow-campaigns render . --out rendered`
writes `rendered/pipelines/<id>.yaml` (a ConfigMap + that pipeline's warm-up
Job) and `rendered/campaigns/<name>.yaml` (a ConfigMap + that campaign's
Indexed Job) for every pipeline and campaign in this repo. Apply pipelines
before campaigns — a campaign's Job references its pipeline's ConfigMap by
name:

```bash
kubectl apply -f rendered/pipelines -f rendered/campaigns
```

`make campaigns-apply DIR=<this-repo>` (from an
[htrflow-batch](https://github.com/AI-Riksarkivet/htrflow-batch) checkout)
does exactly the render + apply above in one step, for the PoC. On a real
deployment, an Argo CD `Application` watches this repo's `rendered/`
directory instead — nothing applies to the cluster that this repo's own CI
did not commit first.

## Results stay

Nothing in this design ever deletes an S3 object. Pausing, cancelling, or
even deleting this whole repo leaves every published `manifest.json`,
`page/`, `alto/` and `iiif.json` exactly where it was. Retention policy is
future work (tracked as htrflow-batch story T10) — until it exists, results
are kept forever.
